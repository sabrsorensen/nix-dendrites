# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Dendritic-pattern Nix flake managing multiple NixOS hosts (and Home Manager
profiles) from one repository. `import-tree` auto-imports every `.nix` file
under `modules/` whose path does not contain `/_`. There is no central
`all.nix` or per-host feature-import list — see "The broadcast-and-gate
model" below before adding or editing any module.

**Read [docs/architecture.md](docs/architecture.md) before adding a host,
feature, service, or flake input.** It is the normative design doc; this file
only summarizes the parts needed to get started and stay out of trouble.

## Commands

```bash
just fmt                          # nix fmt
just check                        # nix flake check (only meaningful once a host's real boot/filesystem config exists)
just checknb                      # nix flake check --no-build (composes configs, doesn't force every toplevel build)
just write-flake                  # regenerate flake.nix (it's DO-NOT-EDIT, generated by flake-file)
just update                       # nix flake update
just install-hooks                # pre-commit install
just run-hooks                    # pre-commit run --all-files
just develop                      # nix develop

# Focused evaluation of one host while debugging (faster than a full check):
nix eval .#nixosConfigurations.<host>.config.system.build.toplevel.drvPath
```

There is no remote bare-metal install/enroll helper right now -- the previous
`scripts/bootstrap-target.sh`/`install-anywhere.sh`/`bootstrap-enroll-remote.sh`
only worked for EmeraldEcho and NixPi and were removed once their
`<host>-bootstrap-image` naming assumption drifted from EmeraldEcho's actual
`<host>-installer` outputs. The underlying per-host bootstrap plumbing
(`my.host.tags` containing `"bootstrap"`, `my.host.bootstrap.finalConfigName`,
`modules/tooling/bootstrap-enroll/`) still exists and still works via `nix
build`/`nix run github:nix-community/nixos-anywhere` directly; a general
driver will be designed fresh when the next bare-metal bringup happens.

`flake.nix` is generated — never hand-edit it. Add/change an input in
`modules/dendritic/dendritic.nix` (bootstrap inputs) or beside the module
that consumes it, then run `just write-flake`. A pre-commit hook also
regenerates it and runs `nix flake check` automatically.

Git-add new files with `git add -N path/to/file.nix` before evaluating —
Nix reads the Git snapshot, so untracked files are invisible to it.

## The broadcast-and-gate model

Every NixOS module registered in `flake.modules.nixos` is evaluated for
*every* host:

```nix
modules = builtins.attrValues config.flake.modules.nixos ++ [ hostFacts ];
```

Consequently:

- A reusable module must be safe when its capability is absent, and must
  activate only via `lib.mkIf config.my.host.<bucket>.<name> { ... }`.
- Never conditionally *import* an ordinary broadcast module from a host —
  that recreates the hidden selection graph this structure exists to avoid.
  Gate configuration, not the import.
- The exception is when an input's option surface is itself unsafe to
  broadcast (unconditional platform behavior, assertions, special-arg
  requirements) — first try neutralising the offending input modules
  (`disabledModules` + re-adding the behaviour under the platform gate, as
  `jovian.nix` does), and only host-scope the import at the output boundary
  as a last resort, with the reason recorded. See "Platform inputs" in
  docs/architecture.md.
- Home Manager features follow the same pattern via
  `dendritic.homeManagerModules`, composed once at the managed-user
  boundary — never a `flake.modules.nixos.home-<program>` module that just
  imports an equivalent Home Manager module.

## Host facts (`my.host`)

Every host declares intent directly, no descriptor builder:

```nix
my.host = {
  name = "Kamino";
  formFactor = "laptop";       # laptop | desktop | handheld | server | vm
  platform = "generic";        # generic | rpi | steamdeck | wsl
  roles = { workstation = true; builder = true; };   # operational responsibility
  features = { gui = true; docker = true; nvidia = true; };  # capability/policy toggles
  services = { minecraft = true; };                  # hosted services
};
```

Module authors read `my.host.is.*` (derived booleans) for broad
classification, `my.host.features.*` / `my.host.services.*` for concrete
activation. Avoid host-name checks except for genuine hardware-edge facts.
Some aggregate features (`features.gui`, `features.decky`, `personalMcp`,
`impermanence`) set component defaults via `lib.mkDefault`; components still
gate on their own narrow feature flag so a host can override one piece.

`features.docker` and `features.podman` are intentionally separate — no
generic "containers" switch. A service needing OCI containers must not
silently pick a runtime for the host.

## Module directory responsibilities

- `system/` — baseline NixOS policy, host-fact schema, locale, boot
  presentation, local DNS, Nix integration (`system/nix/`).
- `platforms/` — reusable OS/hardware integration (RPi, WSL, Steam Deck, x86
  defaults), gated on `my.host.platform`.
- `features/` — optional user-facing/local-host capabilities; a feature owns
  its implementation and non-Nix assets together.
- `services/` — hosted service implementations; service scripts/templates
  live beside the module.
- `home/` — reusable Home Manager policy and user-facing assets.
- `tooling/` — repo/deployment/CLI workflow support; tooling-only Nix
  integrations live in `tooling/nix/`.
- `hosts/<name>/` — host outputs and genuinely host-local facts only
  (`host.nix`, `hardware.nix`, etc.) — organization, not an import
  aggregator. A private `_` helper may live alongside.

Host-specific config is a `hosts/<host>/<concern>/<concern>.nix` +
`_<concern>.nix` pair: the public file registers
`flake.modules.nixos.<concern>-<host>` gated on
`config.my.host.name == "<Host>"` and imports the private payload — broadcast
like everything else, only the gate is host-specific (`hardware-zaphodbeeblebrox`,
`services-atlasuponraiden`). The same shape carries a per-host override of a
broadcast feature that owns a big mostly-shared settings body (e.g.
`programs.plasma`): base keeps only values identical on every host, each host's
delta lives in `hosts/<host>/<concern>/_<concern>.nix` and is applied via
`home-manager.users.<user>.programs.<x>` from the gated NixOS module — never a
second `dendritic.homeManagerModules` entry. See "Host-specific overrides" in
[docs/architecture.md](docs/architecture.md).

CPU architecture and platform integration are different concerns (e.g. Steam
Deck is `x86_64-linux` *and* `platform = "steamdeck"`) — don't invent a new
architecture layer just because a host has a special integration stack.

## Editing discipline

- Read a file's current on-disk contents in the current worktree before
  patching it — never patch from memory or a stale chat/terminal excerpt.
- If a patch fails to apply, stop and re-read the target rather than forcing
  a broadened match against the stale version.
- Verify a file's parent directory exists before creating it; don't assume
  Write/Edit creates missing parent directories.

## Validation notes

- `nix flake check --no-build` composes configurations but doesn't
  necessarily force every host's toplevel build — before a first activation,
  evaluate that host's exact `config.system.build.toplevel.drvPath` to catch
  activation-only errors (e.g. unresolved `/etc` entries).
- Only run the full `nix flake check` once every checked host has its real
  boot/filesystem configuration — an assertion about a missing root
  filesystem means that host edge genuinely isn't ported yet.
- Generated helper scripts (`writeShellApplication`) are ShellCheck-clean;
  guard every path component in deletion commands (e.g. `${var:?}`).
